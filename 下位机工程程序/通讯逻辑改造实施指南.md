## 3. 设计结论

### 3.1 不能删除应用层命令新鲜度监控

EtherCAT 或驱动器 watchdog 监控的是实时过程数据或从站通信，不能可靠判断 Windows 上位机是否停止更新 G.refer。若 ADS 主机进程停止而 PLC、NC 和 EtherCAT 仍然运行，底层总线可能完全正常，PLC 仍可能继续使用最后一次命令。

因此必须保留一个 PLC 应用层命令新鲜度监控。但它不能替代实体急停、STO、TwinSAFE 或安全限位，也不能把一次普通 Windows 调度延迟直接当作永久轴故障。

### 3.2 三层职责

| 层级 | 负责内容 | 修改要求 |
|---|---|---|
| 安全层 | 实体急停、STO、TwinSAFE、FSoE、安全限位、驱动器安全故障 | 保持原逻辑，立即停机或锁存，不由 ADS 自动清除 |
| 运动层 | NC、EtherCAT、MC_Power、MC_Stop、MC_MoveAbsolute、外部设定点 | 保留 PLC 受控停止和实际位置保持 |
| 应用通信层 | Windows 上位机心跳和运动命令是否新鲜 | 改为可恢复通信保持，不直接等同 _err 或实体急停 |

G.estop_hold_req 可以作为“禁止外部运动输出”的聚合请求，但必须能够诊断其来源。至少要区分：

    安全故障
    轴故障
    通信保持
    计划回退停止
    上电未完成
    保持位置或 MC_Stop 错误

### 3.3 恢复绝不自动续跑

通信恢复后必须：

1. 继续保持轴停止；
2. 清除旧的 refer 增量、点动请求、快退旁路和计划回退请求；
3. 读取当前 NC 实际位置并重建设定点基准；
4. 通过 handle_reinit_req/handle_reinit_done 完成重同步；
5. 等待上位机再次执行启动准备或明确的恢复控制；
6. 不补发超时期间的手柄积压位移，不自动恢复旧目标。

## 4. 建议的通信状态机

### 4.1 状态

建议在 handle.TcPOU 内部使用局部枚举，或在 GVL 末尾增加诊断状态：

    InitHold       PLC启动或新会话接管，等待有效心跳
    Online         心跳正常
    SoftHold       短时通信异常，已停止外部运动
    RecoveryWait   心跳恢复，等待停稳和重同步
    FaultHold      长时间失联、停稳失败或恢复异常

如果不增加枚举，可以使用内部 INT，但不得只依靠多个会互相覆盖的 BOOL 推断阶段。

### 4.2 心跳判定

复用 host_session_id、host_heartbeat_sequence 和 host_recover_req：

1. host_session_id=0 时保持 InitHold；
2. 会话号变化时视为新主机接管，清除旧恢复上下文并保持停止；
3. 只有心跳序号变化才算收到新鲜命令；
4. 单次 ADS 读写成功不能作为唯一的主机存活判断；
5. 心跳判定不得与安全急停判定混为一谈；
6. 通信保持期间必须继续每个 PLC 周期调用相关运动 FB，尤其是 MC_Stop。

### 4.3 超时策略

不得把一次约 100 ms 的 Windows/ADS 调度抖动直接升级为永久故障。至少采用两级策略：

    通信保持阈值：连续若干个心跳周期没有变化，进入 SoftHold
    严重故障阈值：SoftHold 持续较长时间仍未恢复，进入 FaultHold

阈值必须根据当前最大速度、停止减速度、PLC 任务周期和允许的最大非预期位移校核：

    检测期间潜在位移 <= 最大速度 * 检测时间
    总潜在位移 <= 最大速度 * 检测时间 + 受控停止距离

阈值集中定义，不得散落在多个分支。可以为现场测试提供比 T#100MS 更大的调度裕量，但最终数值必须由风险评估和现场安全负责人确认，不能只以“不再报错”为依据。

### 4.4 SoftHold

进入 SoftHold 时：

1. 只锁存一次所有业务轴 NC 实际绝对位置；
2. 清除 G.axis1_fast_return、G.axis6_fast_retract、Axis4 点动、注射器点动和计划回退 Req；
3. 保持当前夹爪安全命令，不因通信抖动造成夹爪跳变；
4. 对正在执行的 MC_MoveAbsolute、计划回退和 Axis4 速度运动调用 MC_Stop；
5. 外部设定点使用锁存位置和零速度；
6. 继续调用相关 FB，直到 Done 或明确 Error；
7. 通信保持本身不应把 G.gen_state 改为 _err；
8. G.estop_hold_req 可以为 TRUE，但必须有通信保持原因诊断。

### 4.5 RecoveryWait

收到新鲜心跳后，不得立即解除运动保持。至少要满足：

    心跳连续稳定
    被接管的运动已经停止
    没有安全层故障
    没有正在执行的计划回退
    保持位置输出已经实际生效

然后：

1. 清除 host_timeout_latched；
2. 清除 G.host_recover_req；
3. 置位 G.handle_reinit_req；
4. 等待上位机重建基准并确认 G.handle_reinit_done；
5. 在确认前保持控制未激活；
6. 不自动进入 Follow，不自动恢复旧手柄输入。

### 4.6 FaultHold

以下情况才进入 FaultHold：

- 超时超过严重故障阈值；
- MC_Stop 或保持位置输出明确报错；
- 轴、驱动器或安全链发生故障；
- 恢复握手重复失败并超过限定次数；
- 实际位置无法确认。

FaultHold 必须保留原因和错误码。人工复位必须走正式 PLC 清错/重新初始化流程，禁止由上位机直接强制写 G.estop_hold_req=FALSE 或 G.host_comm_timeout=FALSE 绕过保护。

## 5. 必须修复的恢复死锁

当前 handle 的风险顺序是：

    先计算 all_powered / has_axis_error
    不满足时直接 RETURN
    之后才处理 G.host_comm_timeout

执行 AI 必须改成：

1. 更新会话和心跳状态；
2. 更新通信状态机；
3. 在 SoftHold/RecoveryWait 中锁存位置、清请求、调用 MC_Stop；
4. 再计算轴上电和错误状态；
5. 轴错误进入独立 AxisFault 或 _err 路径；
6. host_all_stopped 只表示运动是否停稳，不能被 all_powered=FALSE 直接阻断；
7. 只有停稳且无安全故障时才清除通信锁存；
8. 清除通信锁存后仍保持控制未激活，等待上位机重同步。

不要简单地把 G.host_comm_timeout 分支移动到最前面并跳过其它逻辑。必须保证：

- 所有实际使用的 MC FB 继续被周期调用；
- 轴错误不会被通信恢复吞掉；
- 通信恢复不会自动重新上电或自动续跑；
- 旧计划回退不会在恢复后重新执行。

## 6. 建议的诊断变量

如正式工程允许增加 GVL 变量，建议只在 GVL 末尾追加：

    host_comm_state              : USINT;  // 0=InitHold, 1=Online, 2=SoftHold, 3=RecoveryWait, 4=FaultHold
    host_comm_reason             : UDINT;  // 最近一次保持原因位
    host_heartbeat_age_ms        : UDINT;
    host_hold_active             : BOOL;
    host_recovery_ready          : BOOL;
    host_all_stopped             : BOOL;
    host_stop_error              : BOOL;
    host_stop_error_id           : UDINT;
    host_last_session_id         : UDINT;
    host_last_heartbeat_sequence : UDINT;
    host_timeout_count           : UDINT;
    host_recovery_count          : UDINT

建议原因位：

    1   无有效会话
    2   心跳超时
    4   新会话接管
    8   计划回退正在停止
    16  Axis4正在停止
    32  轴未上电
    64  轴错误
    128 保持位置或停止FB错误

如果不增加这些变量，也必须在正式状态机文档中说明如何通过现有变量推断保持原因。

## 9. 验证矩阵

### 9.1 正常通信

- 心跳连续发送，状态为 Online；
- 原 7 轴、计划回退、Axis4、注射器和定位臂行为不变；
- G.refer[1..7] 和 G.return_cmd[1..7] 契约不变。

### 9.2 短暂 ADS 或 Windows 调度抖动

- 制造短暂通信间隔；
- 记录进入 SoftHold 的实际时间和原因；
- 确认不自动续跑；
- 恢复后无 refer 跳变、手柄位移补发、快退重复触发或夹爪跳变；
- 稳定心跳并人工重新接管后可以恢复。

### 9.3 上位机进程退出

- Follow 时退出；
- axis1/axis6 计划回退时退出；
- Axis4、注射器或定位臂点动时退出；
- PLC 清除持续请求并停止相关运动；
- 重新启动不会自动续跑旧目标；
- 不需要强制清除 G.estop_hold_req。

### 9.4 轴故障和通信故障同时发生

- 先制造通信保持，再让某一业务轴掉使能或报错；
- 通信状态不能吞掉轴错误；
- 恢复握手不能在轴故障未清除时解除安全保持；
- 清除轴错误后必须有明确的下一步，不得永久卡在不可解释的保持状态。

### 9.5 计划回退中断

- axis1、axis6 和协同回退分别测试；
- 确认只执行一次受控停止；
- 不出现回退完成后再次触发回退；
- 取消后实际位置保持可以确认；
- 模式切换显示准确原因，不再只显示“PLC保持”。

## 10. 禁止的错误实现

执行 AI 不得：

1. 删除全部 host_comm_timeout，让 PLC 永远接受最后一次 G.refer；
2. 只依赖 EtherCAT 或驱动器 watchdog 判断 Windows 主机是否仍在控制；
3. 主机断线后继续执行旧手柄目标或计划回退；
4. 强制写 G.estop_hold_req=FALSE 或 G.host_comm_timeout=FALSE 绕过保护；
5. 恢复后直接写回上一次缓存 G.refer；
6. MC_Stop 未完成时重复下发同一路计划回退；
7. 修改旧 7 轴数组容纳通信诊断字段；
8. 把通信超时直接写成 _err 却没有独立恢复路径；
9. 用实验版 POU 覆盖正式工程 POU；
10. 只改 PLC 源码而不更新正式文档和实现记录。

### 设计思路

- **通信状态如何定义**：
  采用四状态机（`0:WaitHost`, `1:Online`, `2:CommHold`, `3:RecoveryWait`），由局部变量 `host_comm_state_internal` 驱动，外部 ADS 写入无法篡改控制流，`G.host_comm_state` 每周期仅输出镜像。
- **超时阈值和稳定窗口依据**：
  看门狗超时初值设为 250 ms（针对 100 Hz ADS 通信，允许短暂 2-3 帧 Windows 调度抖动，现场记录后可再调优）；恢复握手要求连续稳定心跳 $\ge 300\text{ ms}$（同时约束 `WaitHost` 初始建连与 `CommHold` 故障恢复，彻底杜绝初次启动跳过稳定窗口直接进入 Online）。
- **CommHold 停止收尾与停稳死锁消除**：
  进入保持边沿单次采样实际位置锁存至 `host_hold_abs[i]`，外部设定点以锁存绝对位置和 0 速度刷新；对运行中的计划回退和 Axis4 点动触发 `MC_Stop`；在停止 FB 达成 `Done` 或保持态中明确完成取消收尾（`return_state[i]:=0; G.return_cmd[i].Busy:=FALSE; axis4_manual_state:=0; G.axis4_manual_busy:=FALSE;`），使得 `host_all_stopped` 在机构停止后能立即被真实置位为 TRUE，彻底消除超时卡死在保持态的缺陷。
- **停止错误真实锁存机制**：
  `fb_host_return_stop[i]` 或 `fb_axis4_stop` 报错时，错误码被锁存到 `G.host_stop_error_id`，不再每周期无条件清零；该错误码置位原因位 Bit 7 并阻断自动恢复，只有在显式 `G.handle_reinit_req` 重初始化或清除故障流程时才归零。
- **RecoveryWait 重同步与双端协同边界**：
  必须满足稳定心跳 $\ge 300\text{ ms}$ + 上位机发送 `host_recover_req` + 机构全要素停稳 + 无轴硬件错误与停止错误。进入重同步时置位 `G.handle_reinit_req` 并请求 `G.SetPointGenEnable`，等待 `SetPointGenEnable_output[i].Done` 达成并以当前实际 NC 位置重建基准后置位 `G.handle_reinit_done`，确认无误才转入 `Online` 并解除锁存与握手。
  **双端协同边界明确**：PLC 侧负责将 `G.refer` 与滤波队列对齐到实际当前位置、清零所有回退/点动/快退请求；上位机侧在收到 `G.handle_reinit_done`（或超时恢复）后，**必须清零自身的手柄积分与命令缓冲区，以实际 NC 位置重新锚定控制基线**，方可恢复 ADS refer 下发，绝不补发旧命令。
- **哪些条件进入 FaultHold / _err**：
  轴硬件错误、驱动器报警或急停安全链断开才触发 `G.gen_state := _err`；通信中断停留在可安全恢复的 `CommHold`，彻底解耦通信抖动与硬件急停。
- **如何避免 all_powered/轴错误导致恢复死锁**：
  解除了前置直接 `RETURN`；所有状态监测、停止状态收集和 MC 功能块在每周期均执行调用；`host_all_stopped` 基于速度与 FB 状态真实计算。
