# 实验记录与 Action 4 相机说明

更新时间：2026-08-03
适用模块：`ads_communication.*`、`experiment_recorder.*`、`async_csv_writer.h`、`action4_camera.*`、`main.cpp`、`AdsControlUI`

## 1. 功能边界

统一实验记录由 WPF 的“开始实验记录”和“停止实验记录”唯一控制。一次会话可同时包含：

```text
force.csv
motion.csv
video.mp4                 # 相机成功时
video_frames.csv          # 相机成功时
force_transition_001.csv  # 会话中启动力过渡实验时
session.json
```

开始记录不要求控制激活、力反馈开启、PI 开启、已经调零或相机在线。硬性条件只有：

1. WPF 已连接 C++ 命名管道；
2. C++ 能创建会话目录；
3. `force.csv` 和 `motion.csv` 能打开并写入表头。

记录开始/停止不改变机器人控制、力反馈开关、主从位移 PI、运动模式或力过渡状态机。停止统一记录时，正在运行的力过渡实验继续，只关闭其专用 CSV。

## 2. 操作步骤

1. 启动 `ADS.exe`，再启动 `AdsControlUI.exe`，确认界面已连接。
2. 在主界面“实验记录”区输入实验名称；可留空。
3. 需要检查视野时先打开“相机预览”，预览不要求先开始记录。
4. 点击“开始实验记录”。界面进入“记录中”即表示两个主 CSV 已创建；相机状态单独显示。
5. 实验结束点击“停止实验记录”。等待“正在停止并封装”回到“空闲”后，再关闭程序或移动文件。

`Starting/Recording/Stopping` 期间重复开始/停止请求会被 UI 禁用或被 C++ 忽略。

## 3. 会话目录与名称

目录固定创建在 C++ 当前工作目录下：

```text
records\YYYYMMDD\HHMMSS_实验名称[_001]\
```

名称规则：

- WPF 以 UTF-8 发送，C++ 转为 UTF-16 并使用宽字符 Windows API；
- 保留中文；控制字符和 `< > : " / \ | ? *` 替换为 `_`；
- 去掉首尾空白、末尾空白和末尾点号；
- 空名称使用 `session`；
- `CON/PRN/AUX/NUL/COM1..9/LPT1..9` 及带扩展名形式前置 `_`；
- 最多保留 64 个 UTF-16 code unit，不在高代理项中间截断；
- 同一秒同名目录已存在时依次使用 `_001`、`_002`，不覆盖旧数据。

WPF 输入框使用外置标签和原生 `TextBox`，`MaxLength=64`。记录期间锁定编辑；中文 IME、退格、Delete、选择替换和撤销由 WPF 原生文本编辑处理。

## 4. 统一时间轴

`SessionClock` 在会话开始时记录：

- `QueryPerformanceCounter` anchor；
- QPC frequency；
- 对应的 UTC FILETIME 起点。

每行只写 `elapsed_us`，UTC 起止时间和 QPC 参数写入 `session.json`。这样避免每个控制拍做 UTC 转换。

100 Hz ADS 通信线程在整次快速 Sum Read 调用前后各取一次 QPC，使用中点作为该统一快照的采样时刻。TCP DAQ 使用采集 worker 收到完整帧时的 QPC。视频使用 Source Reader 回调时 QPC，并保留设备源时间戳。

力和位置记录由同一组主机侧 ADS 快照序号驱动：

- ADS 快速快照：100 Hz，QPC 绝对截止时间约每 10 ms 一次；
- `force.csv`：每个 ADS 尝试序号最多写一行，目标 100 Hz；
- `motion.csv`：取偶数 `attempt_sequence`，目标 50 Hz、约 20 ms；
- 主循环一次排空自上拍以来的主机侧快照队列，不伪造历史数据；队列溢出、序号空洞、会话开始前帧和重复帧均单独计数。

快照序号是 C++ `AdsFastSnapshot::attempt_sequence`，不是 PLC `write_sequence`。PLC 不为记录器维护环形缓冲；主机侧仅用 2048 帧队列跨越控制主循环与 CSV 入队节奏。30 fps 视频帧间隔约 33.3 ms，因此只能保证帧时间戳映射，不能把真实曝光事件描述为小于 10 ms 的曝光时间分辨率。

## 5. force.csv

固定表头：

```text
sample_index,elapsed_us,sample_valid,calibrated_valid,
fn_1_raw_v,ft_1_raw_v,fn_1_zero_v,ft_1_zero_v,
clean_force_n,clean_handle_torque_nm
```

纯净值严格定义为：

```text
clean_force_n = 1.913504 * (fn_raw_v - fn_zero_v)
clean_handle_torque_nm = 18.440851 * (ft_raw_v - ft_zero_v) * (3 / 37) * 0.001
```

纯净值不经过重力补偿、串扰矩阵、`k_feedback`、死区、限幅、轴向符号、模式门控、快退锁存、PI 或力过渡处理。

有效性语义：

| 情况 | `sample_valid` | `calibrated_valid` | 原始电压 | 零点/纯净值 |
|---|---:|---:|---|---|
| 采样成功且已调零 | 1 | 1 | 数值 | 数值 |
| 采样成功但未调零 | 1 | 0 | 数值 | `NaN` |
| ADS/TCP 采样失败或过旧 | 0 | 0 | `NaN` | `NaN` |

ADS 为力源时，`force.csv` 直接消费每个 100 Hz 快速快照，不再从更高频/更低频的“最新值”二次截取。失败快照仍保留该时刻，写成 `sample_valid=0` 和 `NaN`；恢复后的新快照不会回填故障空洞。TCP_DAQ 为显式力源时，行时刻仍由 ADS 快照槽确定，仅当最近 TCP 帧与该时刻足够接近才标记有效。仅使用 TCP 回退源、只有 PI 开启且没有统一会话时，力健康消费节流为约 20 Hz 且不产生文件；ADS 快速 Sum Read 本身仍维持 100 Hz。

## 6. motion.csv

固定表头：

```text
sample_index,elapsed_us,position_valid,
axis1_from_left_mm..axis7_from_left_mm,
axis1_handle_valid,
axis1_handle_linear_raw,axis1_handle_linear_filtered,
axis1_handle_rotation_raw,axis1_handle_rotation_filtered,
axis6_handle_valid,
axis6_handle_linear_raw,axis6_handle_linear_filtered,
axis6_handle_rotation_raw,axis6_handle_rotation_filtered
```

7 轴位置来自同一份 PLC 快照：

```text
axisN_from_left_mm = Act_pos[N] + init_pos[N] - leftlimit[N]
```

7 轴位置直接来自偶数序号的 100 Hz 统一快照，不额外补做 ADS 读取。读取失败时 `position_valid=0` 且 7 轴为 `NaN`。两只逻辑手柄按 QPC 选取距离该位置快照最近、相差不超过 10 ms 的输入；没有足够接近的手柄样本时对应 `handle_valid=0`，其四个值为 `NaN`。

单手柄模式下两个逻辑角色可映射到同一个已就绪物理输入；实际序列号和 `single_handle_mode` 写在 `session.json`。

## 7. 力过渡专用表

力过渡状态机与磁盘解耦：

- 没有统一会话时可正常运行，不创建文件；
- 只有在“开始力过渡实验”的瞬间统一会话已经处于 Recording，才创建 `force_transition_001.csv`；
- 会话在力过渡中途才开始时不补建残缺表；
- 统一会话在力过渡中途停止时专用表关闭，状态机继续；
- 同一会话后续实验使用 `_002`、`_003`。

表头：

```text
elapsed_us,valid,trial_id,velocity_level,repeat_in_level,
phase_code,phase_elapsed_ms,v_ratio,axis1_from_left_mm,
clean_force_n,clean_handle_torque_nm
```

`valid=0` 时位置或纯净力不可用，相应测量值写 `NaN`。相位编号见 [力过渡实验使用说明.md](力过渡实验使用说明.md)。

## 8. 异步写盘与故障

`AsyncCsvWriter<Row>` 是单生产者/单消费者环形队列。控制线程只复制一行并移动原子 head；后台线程负责文件写入、每 64 行 flush、停止排空和错误检测。

行为约定：

- 队列满时丢当前行并累计 dropped；
- `force.csv`、`motion.csv`、力过渡专用表或 `video_frames.csv` 发生致命写盘错误时，统一会话自动进入 Stopping；
- 自动停止会尽力封装已有 MP4，并写最终 `session.json`；
- 自动停止不关闭 PI、力反馈或机器人运动控制；
- 程序正常退出复用 `stop_and_wait("program_exit")`，等待 CSV 排空和 MP4 Finalize。

两个主 CSV 在开始阶段任一失败时，本次启动回滚，不留下空会话目录。相机打开、编码或设备错误不影响两个主 CSV，会话继续。

ADS 单拍失败、软保持和自动重连不会自动停止统一会话。记录器继续按快照尝试序号写入无效行，并在 `session.json` 记录失败、重连和序号空洞。PLC 重启/应用重载会让运动控制进入更严格的人工恢复锁定，但记录会话仍保持开启，便于保留故障前后证据；现场可根据实验规程手动停止会话。

## 9. Action 4 探测与录像

### 9.1 设备定位

Media Foundation 枚举视频采集设备，优先匹配 symbolic link 中的：

```text
VID_2CA3&PID_0023
```

找不到 VID/PID 时按 friendly name `OsmoAction4` 备用匹配。找不到设备时状态为 `Missing`，UI 显示：

```text
无法找到摄像设备：OsmoAction4
```

会话仍记录两个主 CSV，不创建空 MP4。

### 9.2 格式选择

候选顺序：

1. 1920x1080@30 H.264；
2. 1920x1080@30 MJPEG；
3. 1280x720@30 H.264/MJPEG/可解码格式。

H.264 候选必须带 `MF_MT_MPEG_SEQUENCE_HEADER`，并在最多 60 个输入样本内出现首个 clean point；失败后尝试下一候选。MJPEG/720p 候选也会预读首个有效样本，预读样本保留为正式首帧。

当前输出固定为：

```text
MP4 / H.264 / 无音频 / 20 Mbps / 实际输入分辨率与 30 fps
```

相机本体的防抖、视场和其他成像设置由相机端负责。程序通过 UVC/Media Foundation 录制，不调用 DJI 移动端控制 API，也不能把相机本体的“2.7K 4:3”菜单设置强制写入 UVC 流。

### 9.3 当前 H.264 管线限制

代码会优先选择并验证相机原生 H.264 候选，但当前 Source Reader 随后统一解码为 RGB32，再由 Sink Writer 编码成 H.264。也就是说，**目前不是压缩码流直接复用**。

这保证了同一采集流可同时用于 1280x720 BGRA 预览和 MP4，但会增加相机 worker 的 CPU/GPU 编解码负担。`video_frames.csv` 的 `keyframe` 是输入样本 clean-point 标志，在转码路径下不等同于最终 MP4 编码器的精确关键帧位置。若后续必须实现原生 H.264 直通，需要增加独立 H.264 解码支路供预览，并在 Action 4 实机上验证 SPS/PPS、时间戳和 MP4 sink input type。

## 10. video_frames.csv

表头：

```text
frame_index,source_timestamp_100ns,callback_elapsed_us,keyframe,discontinuity
```

- `source_timestamp_100ns`：Media Foundation 源时间戳；
- `callback_elapsed_us`：读取该帧时映射到统一会话 QPC 的时间；
- `keyframe`：输入样本 clean-point 标志；
- `discontinuity`：输入 discontinuity 或 stream tick；
- 相邻源时间戳超过 1.5 帧时累计 `dropped_frames`；
- 旁车队列丢行和 writer 错误另写入 `session.json`。

写 MP4 前将源时间戳减去首帧时间，保证文件从 0 开始。每个输入样本设置 30 fps 帧时长。

## 11. 相机状态与拔线行为

状态枚举：

```text
Closed / Opening / Previewing / Recording / Missing / Disconnected / Error
```

录像中拔线：

1. 停止接收新帧；
2. 尽力 Finalize 已写 MP4 和关闭旁车；
3. 状态保持 `Disconnected`，两个主 CSV 继续；
4. 当前会话不自动重连，不创建第二视频段；
5. 下一会话或重新打开预览才重新探测。

正常停止会等待编码器启动中的竞态完成，再等待 MP4 Finalize，避免 UI 已回到 Idle 但后台仍在写上一个会话文件。

## 12. 预览

预览可独立打开。C++ 将采集帧缩放为 1280x720 BGRA32，写入版本化双缓冲共享内存并触发命名事件；WPF 复核写前/写后 sequence，避免撕裂。

预览支持窗口最大化、1x 到 8x 鼠标滚轮缩放、左键拖拽和平移、一键适应居中。变换不修改录制原图。

关闭预览窗口：

- 未录像：释放相机采集；
- 正在录像：停止发布预览帧，录像继续。

共享内存布局和名称见 [可视化界面架构说明.md](可视化界面架构说明.md)。

## 13. session.json

最终元数据包含：

- 原始/清洗后实验名称；
- UTC 起止时间、QPC anchor/frequency；
- 力/位置目标采样率（100/50 Hz）；
- axis1/axis6 逻辑手柄序列号和单手柄模式；
- 两个主 writer、力过渡 writer 的 dropped 和调度 missed；
- ADS 连接终态、实际频率、快照数据龄、RTT、失败/连续失败、重连、PLC 重启和主机快照队列丢帧；
- force/motion/力过渡各自的首末主机快照序号、接受数、无效数、会话前拒绝、重复拒绝和序号空洞；
- 停止原因；
- 相机终态、原生输入格式、输出 H.264/无音频、实际宽高帧率；
- 视频帧数、源时间戳丢帧数、旁车丢行、旁车错误和 HRESULT。

记录启动时先写一份 `utc_end=null` 的元数据；停止封装完成后覆盖为最终版本。

## 14. 已完成验证与实机待验

2026-07-29 已完成（统一会话/相机基础版）：

- C++ 与 WPF x64 Debug/Release 构建；
- 协议 C++ `static_assert` 和 C# wire size 校验；
- 无相机合成会话：中文/非法字符、空名称、保留名、`_001`；
