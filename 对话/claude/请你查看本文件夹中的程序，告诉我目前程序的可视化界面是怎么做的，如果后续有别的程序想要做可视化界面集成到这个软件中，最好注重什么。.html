窗口管理机制



主窗口 MainWnd 通过一个 类型注册表 (ViewTypes 字典) 管理所有子窗口。每个子窗口实现 ILocalWnd 接口，通过反射动态实例化：

Activator.CreateInstance(ViewTypes[tag], this)


如果要集成新的可视化界面，需要注意：



1. 实现 ILocalWnd 接口 — 这是窗口生命周期管理的统一契约（Show()、Close()、Closed 事件）。不实现这个接口的窗口无法被主窗口管理。

2. 使用 DecoratedWnd<T> 包装器 — 如果你的窗口是第三方的或不方便直接实现接口，可以用这个包装类适配。

3. 在 ViewTypes 字典中注册 — 在 MainWnd.xaml.cs 中添加你的窗口类型映射，主窗口才能发现和创建它。

4. 遵循主题资源 — 合并 Colors.xaml、Ribbon.xaml 等资源字典，保持视觉一致性。

5. C++/CLI 互操作模式 — 如果涉及原生渲染（如 VTK、OpenCV），参考 vtk4wpf 的做法：C++ 逻辑编译为 DLL，通过 C++/CLI 桥接层暴露给 WPF，用 WindowsFormsHost 嵌入。

6. 模块系统的端口约定 — 如果新界面需要接入数据流，遵循 Port/InputPort/OutputPort 的类型化数据流模型，支持的数据类型包括 point2d/3d、curve、polygon、mesh、image 等。

7. 线程模型 — WPF 是 STA 线程模型。如果新界面需要独立线程，使用 ThreadWnd<T> 基类在独立 STA 线程中运行窗口。

8. 编译输出路径 — 托管 DLL 放 build\[Config]\bin\，原生 DLL 放 build\[Config]\bin\plugins\。

简单来说，核心集成点就是：实现 ILocalWnd → 注册到 ViewTypes → 合并主题资源。如果有原生渲染需求，走 C++/CLI + WindowsFormsHost 的路线。

从你项目现有模式来看，有三个层次的选择：

1. C++/CLI 桥接（项目已在用，推荐）

直接把 C++ 类包装成 .NET ref class，WPF 端像调用普通 C# 对象一样使用。适合紧耦合、高频调用的场景。你的 vtk4wpf、mod4wpf 都是这个模式。

2. 共享内存 / Memory-Mapped File

适合大数据量（图像帧、点云）传输，C++ 端写入，C# 端读取，零拷贝。适合两个独立进程之间通信。

3. 命名管道 / Socket

适合 C++ 程序作为独立进程运行、需要解耦的场景。灵活但延迟略高。

建议： 如果 C++ 控制程序能编译为 DLL，优先用 C++/CLI 桥接——你项目里已经有成熟的模式（xxx4wpf 系列），团队熟悉，调用开销最小，还能直接支持 WPF 数据绑定（通过 INotifyPropertyChanged）。只有当 C++ 程序必须作为独立进程运行时，才考虑共享内存或管道。
